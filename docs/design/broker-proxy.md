# Broker Proxy

The broker proxy forwards the Microsoft identity broker D-Bus service (`com.microsoft.identity.broker1`) from the container's session bus to the host's session bus. This enables host-side applications (Edge, VS Code, MSAL libraries) to transparently use the container's Intune enrollment for SSO.

## How It Works

```
Host app (Edge)  →  Host session bus  →  intuneme broker-proxy  →  Container session bus  →  microsoft-identity-broker
```

The proxy listens on the host's session bus under the well-known name `com.microsoft.identity.broker1` and forwards method calls to the same service running inside the container.

## D-Bus Interface

Bus name: `com.microsoft.identity.broker1`
Object path: `/com/microsoft/identity/broker1`
Interface: `com.microsoft.identity.Broker1` (note: capital B)

**Methods (8 total):**
- `acquireTokenInteractively` — Interactive auth (browser popup)
- `acquireTokenSilently` — Silent token refresh
- `acquirePrtSsoCookie` — Primary Refresh Token SSO cookie
- `generateSignedHttpRequest` — Signed HTTP request for device auth
- `getAccounts` — List enrolled accounts
- `removeAccount` — Remove an account
- `getLinuxBrokerVersion` — Broker version string
- `cancelInteractiveFlow` — Cancel in-progress interactive auth

All methods accept and return string parameters (JSON-encoded payloads).

## Setup Requirements

The broker proxy requires several pieces of infrastructure:

### Runtime Directory

A host-side directory (`~/.local/share/intuneme/runtime/`) is bind-mounted as `/run/user/<uid>` inside the container. This makes the container's session bus socket accessible from the host at `~/.local/share/intuneme/runtime/bus`.

### Systemd Linger

Linger must be enabled for the container user so that the user session (and session bus) persists even without an active login. `start` enables linger on every run, with or without proxies.

### Login Session

A login session must be created inside the container so that the session bus socket is initialized. The `start` command creates this via `machinectl shell <user>@<machine> /bin/bash --login -c "exec sleep infinity"`. The login shell sources `intuneme.sh` (initializing keyring, display, etc.) and stays alive via `sleep infinity` so the keyring daemon persists. The `start` command waits up to 30 seconds for the session bus socket to appear.

### D-Bus Service Activation

When enabled, a D-Bus service file is installed at `~/.local/share/dbus-1/services/com.microsoft.identity.broker1.service` that triggers `intuneme broker-proxy --root <root>` on first access to `com.microsoft.identity.broker1`. This enables lazy activation — the proxy starts automatically when an app needs it.

`DBusServiceFileContent(execPath, root) (string, error)` passes `--root` so a D-Bus activated instance writes the same PID file (`<root>/broker-proxy.pid`) as the one `intuneme start` uses. It returns an error when an argument contains a NUL byte, because a service-file value cannot carry one.

dbus-daemon parses an `Exec` value in two layers, and the generator handles both:

1. **Service-file layer** (`bus/desktop-file.c`, `unescape_string`): a backslash starts an escape, and only `\s`, `\t`, `\n`, `\r` and `\\` are valid. Any other escape makes the whole file invalid. `escapeServiceFileValue` doubles literal backslashes and writes newline, carriage return and tab as `\n`, `\r` and `\t`.
2. **Command-line layer** (`dbus/dbus-shell.c`): shell-like splitting and unquoting. `quoteExecArg` wraps an argument in single quotes when it has characters outside the safe set; an embedded `'` becomes `'\''`, and inside single quotes the shell layer keeps everything literal.

The service file is generated by joining the layer-2-quoted arguments and then escaping the whole command line for layer 1. `TestDBusServiceFileContentRoundTrip` parses the result through both layers (a test-only port of the C code) and requires the exact argv `[execPath, "broker-proxy", "--root", root]` for paths with a space, an apostrophe, a backslash, a double quote, a newline, a tab, `$` and `*`.

**Upgrade note:** only `intuneme config broker-proxy enable` writes the service file. `start` does not rewrite it. A service file written by an older release has no `--root`; run `intuneme config broker-proxy enable` again to refresh it.

## Enabling/Disabling

```bash
intuneme config broker-proxy enable   # Sets flag, installs D-Bus service file
intuneme config broker-proxy disable  # Clears flag, removes D-Bus service file, stops proxy
```

The `start` command automatically launches the proxy if the flag is set.

## Process Management

- PID file: `~/.local/share/intuneme/broker-proxy.pid`
- Started as background process with `setsid` for terminal independence
- Startup verified by polling PID file (up to 5 seconds, 500ms intervals)
- The PID file is written only after the proxy owns the bus name, so `start` polling it waits for a working proxy
- A second instance refuses to start when the PID file names a live `broker-proxy` process. On exit, a proxy removes the PID file only if it holds its own PID. These rules come from `runBusProxy()` in `cmd/proxy_run.go`, shared with the notify and screencast proxies
- Stopped gracefully by `stop` command before container poweroff
- `status` command reports proxy running state (see below)

## Diagnostics: who owns the bus name?

`broker.LookupNameOwner` (a function variable, replaced in unit tests so CI needs no session bus) asks the host session bus `org.freedesktop.DBus.GetNameOwner(com.microsoft.identity.broker1)` and then `org.freedesktop.DBus.GetConnectionUnixProcessID(owner)`. `broker.FindNameOwner` adds the process name from `/proc/<pid>/comm`, whether the process is an `intuneme broker-proxy`, and the root that proxy serves. `broker.ProxyRoot(pid)` reads `/proc/<pid>/cmdline` and accepts both `--root X` and `--root=X` (the flag may come before or after `broker-proxy`). A proxy without `--root` serves the default root, `~/.local/share/intuneme`; `FindNameOwner` fills that value in. A relative `--root` is resolved against the owner's working directory, read from `/proc/<pid>/cwd`, not against the caller's (`NameOwner.RootResolved`). If that link cannot be read, the root stays unresolved and `status` never treats it as a match. `intuneme start` also passes an absolute `--root` to the proxy it launches. `proxy_test.go` replaces the `procRoot` variable so tests need no real process.

- **`broker-proxy` error.** When `RequestName` does not return primary owner, the error names the owner: `bus name com.microsoft.identity.broker1 already owned by PID 12345 (microsoft-identity-broker); another identity broker or another intuneme broker-proxy is probably running on the host`. If the lookup fails, the old message `bus name ... already owned` is kept.
- **`status`.** Only when `broker_proxy` is enabled in config, and only when the PID file shows no running proxy, `status` queries the bus. A bus owner counts as this instance's proxy only when it is an `intuneme broker-proxy` **and** its root matches the requested root. Both roots go through `filepath.Abs` and `filepath.Clean` first; symlinks are not resolved. Output:
  - `running (PID N, D-Bus activated)` for a proxy with the same root.
  - `not running (bus name owned by intuneme broker-proxy for root <R>, PID N)` for a proxy with a different root. That is a conflicting instance, not this root's proxy, so it must not hide the conflict.
  - `not running (bus name owned by intuneme broker-proxy with unresolved root "<R>", PID N)` when the owner has a relative root and its working directory cannot be read.
  - `not running (bus name owned by PID N (name))` for any other owner, else `not running`.

  The JSON key `broker_proxy` stays a string.
